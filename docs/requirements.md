## 1. 项目目标与首版范围

开发独立的 MoE 路由采集工具，记录真实推理过程中“调度轮次 → 请求 → 实际输入 token → 模型层 → Top-K 专家”的对应关系，为专家负载分析提供可还原、可校验的数据。

核心优先级：真实、准确、完整、可复现。第一版不设性能优化指标，不要求吞吐或延迟对比报告。允许同步拷贝和等待写入。

首版必须实现并验证：

- vLLM 0.10.1 V1 引擎、Granite MoE、单张 NVIDIA GPU。
- 单请求、多个并发请求、请求动态进入与完成。
- Prefill、Decode，以及分块 Prefill 的 token 对应关系。
- eager 模式，关闭前缀缓存，不使用投机解码。

后续范围：其他模型、新版 vLLM、Ascend、TP/EP 多卡、CUDA Graph、投机解码、前缀缓存。首版保留适配边界，不承诺这些能力已可用。不得仅因模型使用 FusedMoE 就宣称兼容。

## 3. 功能需求

1. 启动时显式开启采集，配置输出目录；默认关闭。首版不要求运行中切换。
2. 获取每轮调度及实际模型执行上下文，记录请求 ID、阶段和实际输入 token 位置。
3. 采集每个 MoE 层实际选中的 Top-K 逻辑专家 ID；权重和 token ID 支持可选保存，默认关闭。
4. 支持并发、不同输入/输出长度、请求动态进入和退出。
5. 支持分块 Prefill，保持原始序列位置连续且对应准确。
6. 排除预热、profiling、padding 等非真实请求数据。
7. 提供有界缓冲、分片保存、读取、完整性校验与基础专家计数。
8. 能导出用户需要的逐 token、逐层明细表。
9. 不包含可视化界面和通信网络仿真；它们属于后续扩展。

## 4. 数据字段与语义

### 4.1 逻辑记录

一条逻辑记录表示：某次实际模型执行中，某个请求的一个有效输入 token，在某个 MoE 层的路由选择。物理存储允许规范化为元数据表和数组，不要求逐行重复所有字段。

| 字段 | 必需性 | 定义 |
|---|---|---|
| `run_id` | 必需 | 一次采集运行的唯一标识 |
| `engine_id` | 必需 | 引擎标识，区分引擎内编号空间 |
| `step_id` | 必需 | 该引擎的调度轮次 |
| `execution_id` | 必需 | 实际模型执行标识；不永久假定与调度轮次一一对应 |
| `request_id` | 必需 | vLLM 内部请求标识 |
| `phase` | 必需 | `prefill` 或 `decode`，按该 token 的实际处理语义判定 |
| `token_position` | 必需 | 本次实际送入模型的 token 在请求序列中的位置，从 0 开始 |
| `layer_id` | 必需 | 原始模型层编号，从 0 开始；不是 MoE 层重新排序的编号 |
| `expert_ids` | 必需 | 实际路由选择的逻辑专家编号数组 |
| `rank_id` | 必需 | 首版为 0；为后续多卡保留 |
| `token_id` | 可选，默认关闭 | 本次实际输入 token 的词表 ID |
| `expert_weights` | 可选，默认关闭 | 与专家 ID 对齐的实际路由权重，文档说明归一化/缩放语义 |

另存客户端测试标签与内部请求 ID 的映射。API 返回的 ID 与内部 ID 不能在未验证时直接视为相同。

### 4.2 必须遵守的口径

- 采集的是输入当前 forward 的 token，不是该 forward 新预测 token 的路由。
- 示例：提示词有 69 个 token，Prefill 输入位置为 0～68，其输出可用于产生第一个新 token；首个 Decode forward 处理该新 token，位置为 69。
- 最后生成的 token 如果没有再次输入模型，就没有它对应的下一次路由记录。禁止直接用输出 token 数推导 Decode 记录总数。
- 专家身份使用 `(layer_id, expert_id)`；不同层同号专家是不同参数实体，可按层分别分析负载。
- 逻辑专家编号不能直接当成物理设备或网络目的地。后续流量分析需另有专家到 rank/副本的映射。
- 共享专家单独描述，不能混入路由 Top-K 统计。
- 专家数、Top-K、MoE 层列表从实际配置和执行路径核实；不能写死为所有模型相同。
- 同一 token 若因合法重算被再次执行，应保留新的执行记录并说明原因；不按请求位置全局去重。首版若无法识别此场景，应明确拒绝或判定不受支持，不能静默合并。
- 同一逻辑记录的重复检查至少区分运行、引擎、rank、执行、请求、位置及层。

示例（仅说明格式，不是真实数据）：

| step_id | request_id | phase | token_position | layer_id | expert_ids |
|---|---|---|---|---|---|
| 12 | req_A | decode | 105 | 0 | [2, 5, …] |
| 12 | req_B | decode | 87 | 0 | [1, 9, …] |
| 13 | req_A | decode | 106 | 0 | [3, 7, …] |

## 5. 错误处理与完整性

首版采用严格实验模式：

- token 映射长度不匹配、专家编号越界、必需层缺失、意外重复等情况必须报错，标记运行不完整。
- 写入失败、磁盘空间不足等视为采集实验失败，不能继续输出“成功”状态。
- 缓冲区满时等待写入，不静默丢记录；异步写入若实现，必须向采集主流程传播错误，避免无限等待。
- 请求取消是正常生命周期事件，保留已执行部分并记录取消状态，不要求生成未执行数据。
- 正常停止尽可能排空缓冲并完成校验；异常退出仅承诺已提交分片可读，正在写入分片可被识别为未完成。
- 只有成功收尾且校验通过才标记完整。无结束标记的运行一律不能推断为完整。
- 失败影响限于当前被采集服务，尽可能正常退出，不执行广泛进程清理。
- 关闭采集时不执行采集专用校验。

需要区分“采集运行完整”与“每个请求均正常生成完成”：用户取消的请求可具有完整的已执行轨迹，但请求终止原因必须保留。

## 6. 实现方式与适配边界

采用“独立 Python 工具包 + vLLM 最小 Python 集成补丁 + 版本适配层”。

- 工具包负责配置、上下文关联、缓存、校验、写入、读取及分析。
- vLLM 补丁仅暴露必要调度/执行上下文、传递关联信息并捕获真实路由结果。
- vLLM 0.10.1 的内部依赖集中在适配层，不散落到公共存储和统计代码中。
- 先检查真实源码、调用链和进程边界，再决定采集位置。不能预先锁定某个函数必然可见全部信息。
- request/token 映射必须遵循实际模型输入排列；不能直接拿调度字典顺序代替 GPU 输入行顺序。
- 明确 API 进程、调度/引擎进程和执行进程之间如何关联上下文；不得假设不同进程共享 Python 全局变量。
- 专家 ID 必须来自实际路由路径使用的 Top-K 结果；禁止重新算一遍 softmax/topk 作为真实路由的替代。
- 不原地修改模型输入、路由张量或推理状态，不改变调度和路由算法来简化采集。
- 复用现有预编译扩展。若必须修改或编译 C++/CUDA，先解释必要性、影响和替代方案，由用户决定是否扩大范围。
- 安装后应可验证实际导入路径；Python 修改正确生效后通常通过重启服务加载。

## 8. 输出格式与基础分析

采用 JSON/JSONL 元数据、分片 NPZ 路由数组及 CSV 统计结果。

| 文件 | 内容 |
|---|---|
| `metadata.json` | schema、模型、框架版本、基础及修改版本信息、MoE 层/专家数/Top-K、生效配置 |
| `requests.jsonl` | 请求映射、开始/结束/取消事件 |
| `steps.jsonl` | 调度轮次、实际执行 ID、有效输入行与请求/位置/阶段的映射 |
| `routes-000001.npz` 等 | 分片专家 ID，以及可选权重、token ID |
| `status.json` | 运行状态、记录及分片计数、错误、完整性结果 |
| `expert_counts.csv` | 离线从有效路由记录导出的专家计数 |

设计文档必须确定 NPZ 的键、维度、类型、行偏移和关联规则。通过显式执行 ID、模型层、token 行标识等关联，禁止仅依赖文件出现顺序。可按执行/层保存二维 `[有效 token 数, Top-K]` 数组，最终布局由实现设计确定。

读取器必须能区分完整分片、未提交分片和缺失引用；完整性校验覆盖元数据与数组之间的关联。

基础分析必须支持：

- 按层、专家统计真实 token 路由选择次数，包含零负载专家。
- 分别统计 Prefill 和 Decode。
- 按请求及调度轮次筛选。
- 导出第 4 节的明细表，保留必要标识用于追溯。
- 对固定 Top-K 的单层有效执行，专家计数总和应等于该层有效 token 次数乘以 Top-K；重算按实际执行次数计入，且可追溯。
- 不完整数据可分析，但输出必须显式标记不完整，不能冒充完整实验。

## 9. 资源要求

不要求性能优化、不设开销比例门槛、不要求吞吐/延迟对比报告。允许同步 GPU→CPU 拷贝和阻塞写入。

仍必须保证：

- 缓冲有上限，不能把整场实验数据无限累积在 RAM 或显存。
- 数据分片保存，及时释放不再使用的 GPU 张量及 CPU 缓冲。
- 关闭采集时不做采集专用拷贝、缓存和文件写入。
- 长时间采集资源可控；工具不能因持续持有历史张量而耗尽内存。

这些属于采集可靠性要求，不是性能优化任务。

## 10. 验收标准

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A01 | 基础服务 | 当前模型真实 GPU 推理成功 |
| A02 | 单请求 | Prefill/Decode 的请求、实际输入位置、模型层和专家 ID 可还原 |
| A03 | 多请求并发 | 不同长度请求同时运行、进入和退出时不串请求；证明确实出现并发执行 |
| A04 | 分块 Prefill | 构造确实跨多个轮次的 Prefill，位置和层记录正确 |
| A05 | 路由真实性 | 对小规模真实执行，以实际路由消费位置的结果交叉核对保存的 ID 和行映射 |
| A06 | 完整性 | 已执行有效 token 在应经过的 MoE 层均有记录，无意外重复/遗漏 |
| A07 | 无效数据排除 | 不混入预热、profiling 或 padding |
| A08 | 文件往返 | 分片可读取，关联无歧义，可导出明细表 |
| A09 | 计数 | CSV 与原始记录重算一致，含零负载专家，阶段可分开 |
| A10 | 请求取消 | 已执行记录保留，取消状态准确 |
| A11 | 停机/异常 | 正常停机完成收尾；异常退出、写失败不会误标完整 |
| A12 | 关闭采集 | 推理正常，无采集数据产生 |
| A13 | 可选配置 | 权重和 token ID 开关及请求过滤按声明生效，权重与专家对齐 |
| A14 | 资源有界 | 小缓冲、多分片连续采集不丢记录，不无限持有历史张量 |

验证要求：

- 核心采集链路必须经过真实 GPU 测试；单元测试和模拟数据仅用于补充。
- 不能只用“文件存在”“数组尺寸正确”证明对应关系正确；必须解释 token 行映射及实际路由核对方法。
- 并发、分块等场景必须提供实际发生的证据。基线参数未触发某场景时，为该用例单独调整参数并记录。
- 不以生成 token 数直接作为 Decode 路由条数；以实际模型执行为依据。
- 不对不受支持的平台或模式标记通过；区分通过、失败、未执行及不适用。
- 写入错误可用受控故障注入验证，不通过填满用户磁盘制造故障。

## 11. Agent 开发流程与操作边界

### 11.1 执行阶段

- 创建开发分支和本地提交。

### 11.3 需要用户明确授权

- 升级或重装 PyTorch、CUDA、vLLM，修改驱动。
- 必须修改或编译 C++/CUDA，或扩大首版支持范围。
- 停止用户已有服务。
- 推送 GitHub、合并或发布版本。

必须保留用户已有工作，不覆盖或重置未知改动。不默认下载大型模型，不广泛杀进程，不伪造数据，不把模拟验证写成真实 GPU 验证。缺少 GPU/环境权限时如实标注未验证，不能宣布整体验收通过。
